# 群内命令交互（@ 机器人 · `/赛事`）—— 设计文档

> **状态：已实现（2026-10-09），尚未部署到服务器。** 本文回答「要不要做、怎么做、
> 哪里会翻车」，以及一份可以照着执行的实施与回滚步骤。
> 实现落在 **`esports.py --listen`** + **`douyu-cmd.service`**（本项目唯一的常驻服务）。
> 相关的发送侧原理见 `deploy/ESPORTS.md`；部署环境见 `deploy/DEPLOY.md`。
>
> **一句话结论：可行，已实现。** 整条链路是**新增**的 —— 在此之前项目是**纯单向发送**，
> 仓库里连一行「接收群消息」的代码都没有。

---

## 1. 为什么是新增，而不是改一改

现在的五条流水线全是 **oneshot 服务 + timer**：

```
timer 到点 → 拉起一个进程 → 干一件事 → 退出
```

| 单元 | 频率 | 干什么 |
|---|---|---|
| `douyu-watch` | 45 秒 | 开播 / 下播提醒 |
| `douyu-watchdog` | 2 分钟 | 体检 + 自愈 + 告警 |
| `douyu-esports-announce` | 每分钟 | 开赛提醒（零网络） |
| `douyu-esports-results` | 每 10 分钟 | 单场战报 |
| `douyu-esports` | 每天 09:30 | 赛程预告 + 登记待结算 |
| `douyu-esports-daily` | 每天 09:40 | 全天整合版（零网络） |

**六个 timer 全部是 `inactive (dead)` 常态**，没有任何常驻进程 —— 这是刻意的：
省内存（这台机器小），也不会因为一个进程僵死而拖垮别的线。

命令交互**天生需要一个常驻的东西**去「听」。所以它是**第 7 个单元**，
而且是这个项目里**第一个 `Restart=always` 的常驻服务** —— 落点就是
**`douyu-cmd.service`**（**没有 `.timer`**，这是个常驻服务不是 oneshot 定时任务）。
**现有 6 个 timer 一行都不改** —— 出问题时把新单元 `systemctl stop` 掉，
整条推送线回到今天的状态，这就是「可一键回滚」的含义。

## 2. 现场事实（2026-10-08 只读侦察实测，不是推断）

> 侦察纪律：**不改配置、不重启容器、不发任何消息**。下面每一条都是读出来的。

### 2.1 NapCat 侧

| 项 | 值 | 怎么知道的 |
|---|---|---|
| 容器 | `napcat`（`mlikiowa/napcat-docker:latest`），已跑 2 周 | `docker ps` |
| 网络 | `napcat_default`（**bridge**） | `docker inspect` |
| 发布的端口 | `127.0.0.1:3000`（OneBot HTTP API）、`127.0.0.1:6099`（WebUI） | 同上 |
| 版本 | NapCat **4.18.28** / OneBot **v11**，`get_status.online = true` | `get_status` |
| 机器人 | QQ `3981665877`，昵称「小组作业成员」 | `get_login_info` |
| 目标群 | `1056302577`「不是CS就是GO」，6 人，机器人是 **admin** | `get_group_list` |

配置文件 `/opt/napcat/napcat/config/onebot11_3981665877.json`：

```jsonc
{
  "httpServers": [ /* 1 条：douyuWatch → 0.0.0.0:3000，token 32 位 */ ],
  "httpClients":     [],   // ← 事件出口，空
  "websocketServers":[],   // ← 事件出口，空
  "websocketClients":[]    // ← 事件出口，空
}
```

两个关键字段：

- **`messagePostFormat: "string"`** —— 群消息的 `message` 是 **CQ 码字符串**。
- **`enableWebsocket: false`** —— 那条 httpServer 只用来**收指令、发消息**。

> **四个事件出口全是空的。** 这就是「项目是纯单向的」的根因 ——
> NapCat 从来没往外推过任何一条事件，所以现有代码里没有、也不需要接收逻辑。

### 2.2 「机器人能看到别人发的消息吗」—— 证到了，两次独立印证

这是整个设计的**前提**。用只读手段验证了两遍：

1. `get_group_msg_history(group_id=1056302577, count=300)` 返回 **299 条**，
   其中 **249 条不是机器人自己发的**，来自 **4 个不同 `user_id`**，
   `post_type` 混有 `message`（别人发的）与 `message_sent`（自己发的），
   角色含 `owner` / `member` —— 历史记录**别人也在里面**。
2. `docker logs napcat` 里有直接的接收记录：

   ```
   [info] 小组作业成员 | 接收 <- 群聊 [不是CS就是GO(1056302577)] [榆桉(...)] [回复消息 ...] @...
   ```

   → NapCat **确实在收**别人的消息，**连 @ 提醒都在**。

### 2.3 @ 判定有多容易

`messagePostFormat` 是 **`"string"`** → `message` 是 CQ 码字符串，
@ 机器人就是**字面量**：

```
[CQ:at,qq=3981665877]
```

**正则即可判定，不必解析数组。** 但要留好后路（见 §6 坑 4）：
如果哪天配置被改成 `"array"`，@ 就变成
`{"type":"at","data":{"qq":"3981665877"}}` —— **两种都要认，不能写死**。

### 2.4 依赖

| 包 | 有没有 | 用在哪 |
|---|---|---|
| `websocket`（websocket-client，**同步**） | ✅ 已有 | 路线 B 正向 WS，零新增依赖 |
| `websockets` / `aiohttp` / `flask` / `fastapi` | ❌ 没有 | 自建 WS/HTTP 服务端才需要 |

路线 A **一个包都不用装** —— 它只用 HTTP API（`urllib`，标准库）。

### 2.5 宿主上不属于本项目的东西（新服务要避开）

- 有 3 个**不属于本项目**的 python3 进程在 `0.0.0.0:8765 / 8766 / 8767` 监听。
- 本项目的东西**全在 `127.0.0.1`** —— 新服务也必须只绑 `127.0.0.1`，别占公网。
- ⚠️ NapCat 日志末尾有一处**内部**报错
  （`parseMessageSegments / parseMessageV2 / parseMessage`，某类消息解析失败）。
  与「收纯文本命令」无关（纯文本不受影响），但值得哪天单独看一眼。

## 3. 两条数据通路

要让「@ 机器人」变成「机器人回一条」，需要**进**和**出**两个方向。
出是现成的（OneBot HTTP API，已经在用）；**缺的是进**。

进有两条路：

```
┌──────────────────────────── 路线 A：轮询 ────────────────────────────┐
│                                                                      │
│   [常驻进程] ──每 N 秒──> GET /get_group_msg_history                  │
│        │                    │                                        │
│        │                    └─ 拿回最近 M 条（含别人发的）             │
│        │                                                             │
│        ├─ 按 message_id 去重（水位线）                                │
│        ├─ 匹配 [CQ:at,qq=...] + /赛事                                 │
│        └─ POST /send_group_msg 回消息                                │
│                                                                      │
│   不动 NapCat 配置 · 不重启容器 · 零新增依赖                          │
└──────────────────────────────────────────────────────────────────────┘

┌──────────────────────────── 路线 B：事件推送 ────────────────────────┐
│                                                                      │
│   NapCat ──主动 POST / 或 WS──> [我们的常驻进程]                      │
│        │                            │                                │
│        │  毫秒级、不轮询              └─ 同样的匹配 → POST 回消息       │
│        │                                                             │
│   必须改 onebot11_*.json 加一个事件出口                               │
│   + 必须改 /opt/napcat/docker-compose.yml 发布新端口（bridge 网络）    │
│   + docker compose up -d 重建容器 → 短暂断线                          │
└──────────────────────────────────────────────────────────────────────┘
```

### 3.1 为什么**先做路线 A**

**判据是「先做能一键回滚的」，不是「哪个更快」。**

| | 路线 A（轮询） | 路线 B（事件推送） |
|---|---|---|
| 动线上服务 | **否** | 是（改配置 + 重建容器） |
| 新增依赖 | **0** | 0（已有 `websocket`） |
| 回滚方式 | `systemctl stop` 新单元 | 改回配置 + **再重建一次容器** |
| 延迟 | 几秒 | 毫秒级 |
| 未验证环节 | **无** | 「事件会不会真的投递到我们进程」 |

最后一行是决定性的 —— 见下面 §5 难点 1。

**目标场景是人工敲命令**（有人想看今天赛程，@ 一下）。
几秒延迟对「查询类命令」毫无价值，但「一次容器重建」有实实在在的 downtime 风险。

> **升级路径留着**：路线 A 跑通、命令真的有人用之后，
> 如果觉得几秒延迟难受，再迁到路线 B。两者**匹配逻辑完全共用**
> （同一份 `parse_command()`），换的只是「消息从哪来」。

## 4. 四道闸门

命令进程会**同时**带来三件新麻烦：多一个改状态文件的进程、多一条触发联网的路径、
多一个能被群里任何人触发的入口。所以四道闸门缺一不可。

```
        用户 @ 机器人 /赛事
                │
                ▼
   ┌────────────────────────┐
   │ 闸门 1 · 命令识别       │  剥掉 CQ 码后「整条恰好相等」才算命令
   │                        │  不做子串匹配；非目标群直接丢
   └───────────┬────────────┘
               ▼
   ┌────────────────────────┐
   │ 闸门 2 · 群内冷却       │  同群同命令 N 秒内只响应一次
   │                        │  防连点刷屏（6 人群也会被点）
   └───────────┬────────────┘
               ▼
   ┌────────────────────────┐
   │ 闸门 3 · 水位线幂等     │  按 message_id 去重；**先发成功、后落盘**
   │                        │  重启 / 时间回拨都不重发
   └───────────┬────────────┘
               ▼
   ┌────────────────────────┐
   │ 闸门 4 · 条款节流       │  复用 parse_gate 的 30 秒跨进程闸门
   │                        │  共用 state_esports_parse.json
   └───────────┬────────────┘
               ▼
        渲染 → 发送（三级降级）
```

| 闸门 | 挡什么 | 现状 |
|---|---|---|
| 1 · 命令识别 | 误触发（「我觉得 /赛事 不错」这种闲聊） | 需新写，逻辑简单 |
| 2 · 群内冷却 | 连点刷屏 → 打满 Liquipedia 请求 → 触发风控 | 需新写，**配置项** |
| 3 · 水位线幂等 | 重启后重放历史 → 刷屏；崩溃后重复发送 | 需新写，**最容易出事** |
| 4 · 条款节流 | 违反 Liquipedia `action=parse ≤ 1 次/30 秒` | **已有 `parse_gate()`，直接复用** |

## 5. 设计流程（五阶段）

### 阶段 ①·只读侦察 —— 已完成（§2）

**判据：把「能不能」从猜测变成事实，而全程不改配置、不重启、不发消息。**

这一步的价值在于：它把后面所有讨论的地基从「应该可以吧」换成「实测可以」。
本文 §2 的每一条都是这一步的产物。

### 阶段 ②·选路线 —— 已完成（§3）

**判据：先做能一键回滚的。** → 选路线 A（轮询）。

### 阶段 ③·做 MVP

范围**刻意压到最小**：

1. **只认配置里那个群**（`channels` 里已有的群号），别的群一概不理。
2. **命令必须「剥掉 CQ 码后整条恰好相等」**才响应 ——
   `[CQ:at,qq=3981665877] /赛事` 剥完是 ` /赛事`，`strip()` 后等于 `/赛事` 才算。
   **绝不做子串匹配**（否则「我想看 /赛事」也会触发）。
3. **输出复用现成的渲染栈**：`build_daily_data` + `render_card_html`
   （就是每天 09:30 那张总预告大图的函数），**不新写版式** ——
   版式多一份就多一处要维护、多一处会走样。
4. **回复带 `[CQ:reply,id=...]`**，让群里看得出是在回哪条。

**MVP 验收 = 在群里真敲一次 `/赛事`，收到今天那张大图。**

### 阶段 ④·加固四道闸门 —— 见 §4

顺序是先跑通、再加固。但**闸门 3（水位线）必须在第一次上线前就位** ——
它的失败模式是「上线即刷屏」，属于不可接受的。

### 阶段 ⑤·上线

1. **先前台手动跑**（不挂服务）：`python3 esports.py --listen`（暂定名），
   观察日志，在群里敲一次 `/赛事`，确认收到正确的大图。
2. 确认无误后，再新增一个 `Restart=always` 的常驻单元
   （`douyu-cmd.service`，**不加 timer**）。
3. **现有 6 个 timer 一行都不动。**
4. 出问题：`systemctl stop douyu-cmd` → 整条推送线回到今天的状态。

## 6. 真正的难点

### 难点 1：「事件推送会不会真的投递到我们进程」用只读手段证明不了

我们可以证明 NapCat **在收**消息（§2.2，两处独立印证）。
但**证明不了**「它配的事件出口会把事件推给我们、我们会收到」。

- 这是**路线 B 独有**的未验证环节。
- 想验证它必须**改配置 + 重启容器** —— 那就是「动线上」，与只读侦察不兼容。
- **路线 A 的价值不只是低风险，而是它绕开了这个未验证环节** ——
  轮询直接消费一个**已经证明可用**的 API（`get_group_msg_history`）。

> 这条是本设计里最重要的一个判断：**优先选「没有未知量」的方案，而不是「理论上更快」的方案。**

### 难点 2：多进程共享状态 —— 改状态文件的进程从 3 个变 4 个

现在 `state_results_pending.json` 有 **3 个**进程在改
（09:30 登记 / 每 10 分钟结算 / 09:40 补漏）。
命令进程一上线就是**第 4 个**（如果它也写待结算清单的话）。

**处理方式与现有完全一致，不发明新机制**：
一律走 `update_pending(apply)` / `update_announce(apply)` ——
「**锁内重读 → apply → 写回**」，合并判据用 `_item_ident()`。
**绝不**用「锁外读到的快照整体覆盖回去」（那是丢更新的根因）。

### 难点 3：绝不在持有状态锁时联网

`/赛事` 要抓页面，而 `parse_gate` 有 **30 秒**最小间隔 ——「等」是**不可避免**的。

一旦把 `file_lock` 包在「等 + 抓」外面：

```
命令进程：  [持有锁] ── 等 30 秒 ── 抓页面 ── 释放
            ↑ 这 30 秒里，每 10 分钟一拍的结算进程会被堵在锁外
```

**规则：状态锁只包「读 + 写」，网络请求一律在锁外。**

> **澄清一处最容易记反的地方**：`parse_gate` 的 `time.sleep` **确实在锁内** ——
> 但它锁的是**自己的专属文件** `state_esports_parse.json.lock`，不是任何状态文件。
> 它**必须**这样：第二个调用者要在锁内**重读时间戳**才能算出真正的剩余等待时间，
> 否则「1 次 / 30 秒」的间隔会被两个进程同时读到旧值而白留。
> 所以「持锁等 30 秒」在这里是**对的** —— 它只阻塞**别的 parse 调用者**，
> 不阻塞结算 / 整合（那些锁的是 `state_results_pending.json`，另一个文件）。
>
> 命令进程要遵守的是：**别拿「水位线的锁」去陪 parse_gate 睡**。而水位线锁
> （`state_cmd_watermark.json.lock`）与 parse 锁本来就不是同一个文件，结构上天然隔离。
> 自检里有一条 **AST 断言**扫源码，钉住「`with file_lock(...)` 里不许出现联网调用」。

### 难点 4：图片体积

| 项 | 值 |
|---|---|
| 1920×1080 PNG | 130 ~ 380 KB |
| base64（×1.37） | ≈ 180 ~ 520 KB |
| QQ 单条消息上限 | 通常 ~ 几十 MB，够用 |

**真正的问题不是「能不能发」，是「会不会被连点」。**
命令是用户触发的、**可能被连点** → 群内冷却不只是礼貌，
它是**带宽与风控预算**。这也解释了为什么闸门 2 是必需的，不是可选优化。

## 7. 最容易真出事的坑（按危险度排序）

### 坑 1 · 🔴 首次启动的水位线（**上线即刷屏**）

常驻进程第一次跑时，如果水位线初始值是 `0`：
它会把群历史（299 条）**全部当成新命令重放** → 群里瞬间被塞满图。

**必须：首跑只记「当前最大 `message_id`」、不响应任何历史消息。**

```
首次启动：
    max_id = max(所有历史 message_id)
    落盘水位线 = max_id
    然后才开始响应 id > max_id 的新消息
```

### 坑 2 · 🟠 水位线必须在「发送成功之后」落盘

与 2026-10-06 那条「送达一条就落盘一条」同源。
如果**先落水位线、再发送**，发送失败时这条命令就永远丢了（水位线已经推过去了）。
反过来（先发后落）最坏是**重复发送一次** —— 两害相权，宁可重复。

### 坑 3 · 🟡 `@全体成员` 的 CQ 是 `[CQ:at,qq=all]`

**不是 @ 机器人**，别误判。判定时必须**精确匹配机器人 QQ**，
不能写「只要有 `[CQ:at,` 就算 @ 机器人」。

### 坑 4 · 🟡 `messagePostFormat` 会翻转

现在是 `"string"`（CQ 码字符串），但**配置是会被改的**。
解析函数**两种都要认**（字符串 CQ 码 / 数组 segment），别写死。
自检里应同时覆盖两种输入。

### 坑 5 · 🟡 回复里带 `[CQ:reply,...]`

有人**引用一条旧消息**再 @ 机器人 —— 那条消息的 `message` 里会带
`[CQ:reply,id=...]`。剥 CQ 码时必须把它剥掉，
**别把被引用的旧内容当成命令的一部分**（否则匹配永远失败，
表现是「明明 @ 了却毫无反应」，很难查）。

### 坑 6 · 🟡 别用 console 通道回消息

`config.json` 里有 console 通道（本地调试用）。它**永远「成功」** ——
会吞掉 onebot 的真实失败判据（`retcode`），
让「其实没发出去」看起来像「发成功了」。**回消息只能走 onebot 通道。**

### 坑 7 · 🟡 失败时**不要在群里回「出错了」**

那等于**故障广播** —— 一炸就是给全群推一条错误。
失败时是「静默」还是「回一句短的」，**属产品决策，需要用户拍板**。
默认建议：静默 + 写日志。

### 坑 8 · 🟡 冷却参数别写死

- 冷却是**配置项**（`cmd_cooldown_seconds`），别硬编码秒数。
- 去重按 **`message_id` + `time` 双水位线** ——
  单靠 `message_id` 挡不住 NapCat 重启（id 可能回退），
  单靠 `time` 挡不住同一秒的多条消息（且有时间回拨风险）。

## 8. 风险分级表

| # | 风险 | 概率 | 影响 | 缓解 |
|---|---|---|---|---|

**实现时的两处偏差（都以代码为准）：**

1. **联网锁**：实际没在命令路径上用 `file_lock` —— 水位线是**单写者**（只有这一个进程写），
   用不着锁；`save_wm` 走原子写（tmp + `os.replace`）。
   于是「联网不在锁内」在结构上天然成立，自检用 AST 断言钉住「`with file_lock(...)`
   里不许出现联网调用」以防将来有人加锁加错地方。
2. **`retry` 字段**：坑 2 说「先发后落」，但**无限重试会打满来源**。
   所以加了 `cmd_max_attempts`（默认 3）：失败时水位线**不推进、暂停本轮**（下轮重试），
   到上限才推进放弃。这是「宁可重复、但别疯狂重试」的折中。
