# 续跑提示词 · 内存处理完之后继续部署

> **用法**：整份复制，发给服务器上的 agent。
> **适用场景**：上一轮预检判定内存「不足」并按规则停下，现在内存已缓解、部署包已更新。
> 若是全新部署，请改用 `AGENT_PROMPT.md`（全流程版）。

---

## 此前发生了什么

上一轮预检判定内存「不足」并按规则停下（典型情形：总内存 ~1.5GB、可用不足 400MB、且没有 swap）。

现在可用内存已缓解到约 **0.8GB**。同时部署包在内存方面做了几处兜底改进：

- 容器内存上限从硬编码改为由 `.env` 的 `NAPCAT_MEM_LIMIT` 控制（现设 `700m`）
- 预检新增「NapCat 预算」= 可用内存 + swap 可用量的一半，判定由三档细化为四档
- 补上一条最容易搞反的规则：**上限必须 ≤ 宿主机可用内存**，否则这道安全网等于没设

---

## 你的任务

从**更新部署包**开始，然后接着 `AGENT_PROMPT.md` 的**阶段 2** 一路做到阶段 8。

---

## 五条硬约束（不变）

1. **这台机器上还跑着别的服务（个人网页）。不要停、不要改、不要删任何现有的容器、systemd 单元或配置文件。**
2. **绝不要执行 `docker compose down -v`** —— `-v` 会删数据卷，QQ 登录态丢失就得重新扫码。
3. **端口只能绑 `127.0.0.1`**。compose 已写好，别改成 `0.0.0.0`，也别去云安全组放行 3000 / 3001 / 6099。
4. **不要修改** `.env` / `config.json` 里的 token、群号、`treat_loop_as_live`，
   **也不要改 `NAPCAT_MEM_LIMIT`**（已按可用内存设为 `700m`）。
5. **扫码登录只能由人完成**。到那一步必须停下来交接。

---

## 第 1 步 · 更新部署包 + 重跑预检（只读）

```bash
cd <上一轮解压 deploy.zip 的目录>
unzip -o deploy.zip          # 覆盖旧文件，这次改动较多
cd deploy
chmod +x *.sh
bash preflight-check.sh
```

`preflight-check.sh` 是**只读**的：不写文件、不重启服务、不装东西。

**新版输出与上一轮不同**，会多出一行 `NapCat 预算:`，并在末尾给出**按当前内存定制的「下一步」**。以它为准。

---

## 第 2 步 · 按新判定处理内存

**用户已预先授权**：若预检提示「没有 swap 兜底 → 先加」，直接执行：

```bash
sudo bash add-swap.sh        # 默认 2G；幂等，可用 --remove 撤销
swapon --show                # 期望：列出 swapfile，大小 2G
free -h                      # 期望：Swap 一行不再是 0B
```

**必须两条命令都确认 swap 真的生效**，才算做完这一步。然后重跑预检：

```bash
bash preflight-check.sh
```

**若重跑后仍判定「[不足]」→ 停下**，把完整输出发回来等指示。不要硬上。

> 如果预检显示**已有 ≥1GB swap**，就跳过 `add-swap.sh`，直接继续。

---

## 第 3 步 · 继续往下做

严格按 `AGENT_PROMPT.md` 的**阶段 2 → 阶段 9** 依次执行，不要跳步。
（阶段 9 是装看门狗 —— 别省。没有它，NapCat 掉线和监控停摆都是静默的，
你只会「什么都没发生」，而不会收到报错。）

其中**四道验证关卡一道都不能跳**：

| # | 命令 | 期望 |
|---|---|---|
| ① | `python3 selftest.py` | 最后一行 `0 项失败`，退出码 0 |
| ② | `python3 watch.py --probe <你的 room_id>` | 两个接口都成功，能看到主播名和 `videoLoop` 字段 |
| ③ | `python3 watch.py --once` | **`判定：未开播`** ← 房间在轮播，这是**正确**结果，不是故障 |
| ④ | `python3 watch.py --test-notify` | **QQ 群里真的出现一条测试消息**（必须由人亲眼确认） |

> **别用项数判断版本** —— 项数会随版本增加，文档里的数字必然过时。
> 要看版本，就比对 `install-watch.sh` 打印的 `watch.py` / `selftest.py`
> sha256 前 16 位；对不上就是旧版 —— 解压最新的 `deploy.zip`，在 `deploy/` 里重跑
> `sudo bash install-watch.sh`（**不会覆盖已填好的 `config.json`**），再重跑 ①。

> ④ 之前先确认小号**已加入目标群**：`curl .../get_group_list` 里能看到群号。
> 看不到就是没加，这是群聊发送失败最常见的原因。

阶段 9 的三道关：

| # | 命令 | 期望 |
|---|---|---|
| ⑤ | `python3 watchdog.py --selftest` | 最后一行 `0 项失败`，退出码 0 |
| ⑥ | `python3 watchdog.py --status` | 心跳 `ok`、NapCat `online` |
| ⑦ | `python3 watchdog.py --test-alert` | **用户真的收到一条测试告警**（必须由人确认） |

> 阶段 9 里有一处**必须停下让用户决定**：告警发到哪个通道。
> 相关背景要说清楚 —— NapCat 掉线时它自己发不出消息，所以
> **必须至少配一条不经过 NapCat 的通道**（`ALERT_WEBHOOK`），否则掉线告警等于没说。
> 别自己替用户编一个地址。

## 出错时的原则（不变）

- **不要反复重试同一条失败的命令**
- **不要为了「让它通过」而放松安全设置** —— 包括放开端口、清空 token、
  把容器内 `host` 改回 `127.0.0.1`、改 `treat_loop_as_live`、**调大内存上限**
- **不要删除或重建任何已有的容器 / systemd 服务**
- 失败就把**执行过的命令 + 完整原始输出**发回来，越原始越好

---

## 最后回报这几项

1. 第 1 步预检的**完整输出**（尤其新增的 `NapCat 预算` 行与判定行）
2. 是否执行了 `add-swap.sh`；`swapon --show` 与 `free -h` 的输出
3. `ss -lntp | grep -E ':(3000|6099)'` → 确认只绑 `127.0.0.1`
4. `docker inspect napcat --format '{{.HostConfig.Memory}}'` → 期望 `734003200`（即 700m）
5. 阶段 9：`watchdog.py --selftest` 最后一行、`watchdog.py --status` 完整输出、
   **告警发到了哪个通道、用户是否真收到**、以及「停摆验证」（故意停掉定时器，等 10 分钟以上）与
   「零风险版掉线检测」（假容器名 + 隔离 state 目录，**不加 --dry-run**，否则告警不会真发）的结果
5. **群里是否真的收到了测试消息**（由人确认）
6. 任何**跳过、失败或你不确定**的地方 —— 直接说，不要掩盖
